# 鉴权匹配的数据结构与性能

运行时接口仍是 `POST /api/v1/authorize`，传入 `appKey`、`serviceResource`、`subject`、`method`、`path`，`domain` 可选，省略或传空白按默认空域处理（旧值 `global` 同样归一为空默认域），请求字段及服务凭证见 [接口参考](reference-api-rbac-v1.md#8-运行时鉴权)。应用组织配置，服务 API 运行时合并所有启用应用的有效授权。本文的 N 指存量策略数据规模，基准按实际绑定数据量生成，不用请求次数代表容量。

> 适用范围：`src/internal/biz/rbac_policy.go` 的应用级编译引擎现在是菜单与全策略适配器的实现，并继续为测试和历史基准服务。运行时 `/api/v1/authorize` 与 `/api/v1/rbac-v1/simulate` 由 `redis.enabled` 选择来源，默认 `true`，省略 YAML 时也为 `true`。启用时走 Redis 服务 API 入口：按 `service + subject + normalized domain` 直接读取完整 String JSON，严格校验身份、大小和内容；不读取 `state`、Lua 或应用辅助 key。JSON 已合并所有启用应用的 Catalog 与用户 API 并集，不按应用隔离。显式禁用时使用数据库 current-policy，且不创建 Redis 客户端或发布记录。菜单始终使用独立 current-policy。本文描述的路由 Trie 与角色位图结构在服务 API 入口中复用；第 5 节的基准测的是应用级引擎，用大绑定量说明线性扫描的替代成本，不代表服务 API String 策略的规模。

## 1. 旧算法的实际开销

旧算法每次读取并解码完整权限记录，遍历全部 API，再遍历全部用户角色绑定，对匹配当前用户的每条绑定遍历全部角色，最后为当前请求重新建立授权 API 集合。

记 E 为 API 数、L 为路径段数、B 为全部用户角色绑定数、K 为当前用户的绑定数、R 为角色数、G 为本次展开的角色授权数，纯匹配约为：

```text
O(E × L + B + K × R + G)
```

外层绑定先过滤用户，所以不是所有 B 条绑定都执行 R 次角色比较；但用户拥有很多角色时，K×R 仍很贵。上述复杂度还不包括数据库、Redis 传输、JSON 解码、校验和计算及分配内存的成本。

## 2. 编译索引

菜单与全策略路径下，每个应用的当前权限第一次被访问时编译成只读 Go 索引：

```text
compiledRBACPolicy
├─ routes[(serviceResource, method)]
│  ├─ exact[规范化路径] → Endpoint
│  └─ dynamic[路径段数] → 参数路径 Trie
├─ principals[(subject, domain)]
│  ├─ 启用角色的稀疏位图
│  └─ 用于 matched_roles 返回值的角色编码
└─ endpoints[Endpoint 序号]
   ├─ id / enabled
   └─ 授予该 API 的启用角色稀疏位图
```

身份键和服务键采用包含独立字段的 struct，避免字符串拼接分隔符造成碰撞。角色序号及 Endpoint 序号只在单次编译的索引内使用，不持久化到 Redis，不跨应用或重建复用。

定义：E 为接口数，R 为角色数，B 为全部用户角色绑定数，G 为全部角色接口绑定数，P 为路由模板的总路径字节/节点规模。索引构建与空间在正常唯一 ID 数据下为平均 **O(P + R + B + G)**；固定路径长度时，记 N = E + R + B + G，即平均 O(N)。哈希操作是平均复杂度，字符串处理还取决于字符串长度。

例如一个角色有 100 万用户、10 万接口：保存 100 万条身份绑定和 10 万条授权关系，不展开成 1,000 亿条用户接口权限。

### 2.1 用户身份：哈希定位

通过 `principals[policySubject{subject, domain}]` 直接取得当前用户的角色位图，不再扫描全应用的绑定表。身份键使用归一化后的 `domain`：省略、空白和旧 `global` 都编译成空默认域，具名域保持各自独立。角色 ID 与角色对象也在编译时用哈希表关联。

**同角色的单角色用户共享一个只读 principal**，其中包含一个角色位图和角色编码列表；100 万用户不会生成 100 万份相同角色集合。每个身份键仅指向该对象。用户出现第二条角色绑定时，采用复制后修改，构建该用户自己的角色集合，避免污染其他用户；构建完成后全部只读。多角色用户按实际 B 条绑定存储，仍不展开角色的接口列表。

### 2.2 路由：静态哈希与参数 Trie

先按服务、HTTP 方法定位路由集合。完整静态路径放入哈希表，例如 `/orders/export`；含完整参数段的路径放入 Trie，例如 `/orders/{id}/items`。

Trie 按路径段数分组，节点包含静态子节点、一个参数子节点、终点匹配信息和子树最大具体度。参数名不影响路径形状，`{id}`、`{name}` 共用同一参数分支；若对应不同 API 且具体度相同，记录为冲突并拒绝。

查询时先取静态路径候选；若同深度参数树不可能提供同等或更高优先级，立即返回。参数查询只进入当前路径可匹配的分支，并用子树最大具体度剪枝。参数只消费一个非空路径段。保留旧实现对路径首尾斜杠的处理方式，不合并内部空路径段。

这里不能采用“静态分支匹配上就直接返回”的贪心路由。例如：

```text
/a/{x}/{y}
/{x}/b/c
```

请求 `/a/b/c` 时，第二条固定段更多，应优先匹配；若只沿 `/a` 静态分支走，就会选错。当前 Trie 会检查必要的参数分支，保留原有的完整路径优先级。相同最高具体度的不同 API 仍返回 `ambiguous_endpoint`；停用的具体 API 也不能退回更宽泛的已授权 API。

### 2.3 授权：稀疏角色位图交集

每次编译给每个角色一个整数序号。用户位图表示“用户拥有哪些启用角色”；API 位图表示“哪些启用角色授予这个 API”。两个集合有交集，即允许访问：

```text
用户角色：{2, 5, 129}
API 角色：{5, 70}
交集：    {5} → 允许
```

每 64 个角色组成一个 `uint64` 字，只保存非零字。单字位图直接用位与判断；多字位图遍历较短集合，并在另一集合的字索引哈希表中查询。字序号参与比较，因此角色 1 与角色 129 不会因为在各自字中的位偏移相同而相互授权。

这避免了为每个用户展开所有 API 权限。位图空间随真实绑定和角色 API 授权增长，整体索引约为 `O(路由节点 + E + R + B + G_total)`，其中 G_total 为全部角色 API 授权数；不会直接分配 `用户数 × API 数` 的权限矩阵，也不会为每个 API 分配包含全部角色的稠密位图。

`matched_roles` 继续保留旧实现的诊断语义和顺序；停用角色不参与位图授权。返回角色编码时复制切片，调用方不能通过修改响应对象污染共享索引。

## 3. 复杂度与边界

| 操作 | 索引后的开销 |
| --- | --- |
| 定位服务和方法 | 平均 O(1) 哈希查找 |
| 定位用户和 domain | 平均 O(1) 哈希查找 |
| 静态路径匹配 | 平均 O(1) 哈希查找，仍需处理路径字符串的哈希/长度 |
| 参数路径匹配 | O(L + V)，V 为实际访问的 Trie 节点数 |
| 判断授权交集 | O(min(Wu, We))，Wu/We 分别为用户/API 角色位图的非零字数；常见单字场景 O(1) |
| 返回角色编码 | O(K)，用于复制返回切片 |
| 首次构建 | 约 O(E×L + R + B + G_total)，与请求匹配分离 |

上表只覆盖匹配函数内部的开销。菜单 current-policy 路径在匹配之前有一层固定成本：读取应用启用状态与当前规范化记录并计算内容摘要，读取配置目录的全部启用服务、按键排序并计算摘要作为缓存身份；这一层的规模由全局服务资源数 S 决定，与本应用绑定的用户、角色和接口数量无关，约为 O(S log S)，远程目录模式还包含一次目录网络读取。Redis 模式的服务 API 路径固定成本是一次 String `GET`，加上严格身份、大小与 JSON 校验，不读取应用元数据或服务目录摘要；显式禁用时改走数据库 current-policy，成本按数据库读取路径计算。请求总耗时至少是“这一层读取 +（可复用编译索引时的）匹配”，不能由下面的纯匹配基准推断。

参数模板大量交叉重叠时，Trie 仍可能访问许多分支；不能把所有情况都承诺为 O(L)。普通路由访问的节点主要随路径长度变化，静态路径不必遍历全部 API。

## 4. 缓存加载与一致性

菜单和全策略适配器走 current-policy 路径：每次请求读取应用启用状态、当前规范化业务表和当前服务目录，计算内容摘要作为缓存身份，然后查询进程内编译索引。

```text
取当前缓存身份（启用应用 + 内容摘要 + 服务目录摘要）
  → 本地索引命中 → 直接匹配
  → 本地索引未命中 → 单条 MVCC 语句读取当前规范化业务表
                    → 校验、编译
                    → 完整构建后加入缓存
```

内容摘要是当前记录规范 JSON 的 SHA-256，只用作进程内缓存身份，不持久化、不进入 Redis key，也不是业务版本。菜单与全策略索引按应用保留，默认上限 64 个，同一应用的新加载替换旧索引，因此每个应用同时只保留一个当前索引；内存命中时不再访问数据库或反序列化完整记录；应用停用、内容变化和数据库读取失败都不能被旧索引绕过。

Redis 模式的服务 API 路径（`/api/v1/authorize` 与 `/api/v1/rbac-v1/simulate`）不读取应用元数据、服务目录摘要或辅助 key：每次请求直接读取该服务、用户与 domain 对应的 String，严格校验身份、大小和 JSON 后匹配完整 Catalog 与合并后的 `apis`。内容相同时可以复用进程内编译索引。String 缺失、类型或内容损坏、身份不匹配和 Redis 错误都拒绝，不读取数据库，也不接受旧应用级 JSON fallback。强制启用时启动就要求 `redis.url` 非空；Redis 禁用时不会进入这条路径，服务 API 使用数据库 current-policy。

同一应用同一内容摘要的并发首次加载通过 `singleflight` 合并加载和编译。单个等待者取消不会取消其他请求共享的加载；共享加载使用独立的 30 秒超时上下文，允许加载和构建。调用方超时可提前结束等待；该截止时间在编译结束后检查，CPU 编译本身不支持中途抢占取消。构建失败不缓存，后续请求可重试。缓存淘汰不影响持有旧只读指针的在途请求。

本地缓存按条目数限制，不是严格的内存字节预算；菜单与全策略索引容量设为 64，服务 API 索引容量设为 1024，大应用或大量应用部署时，需要结合索引大小和实例内存评估这两个上限。冷启动、缓存淘汰或每次重建后的第一次请求仍要付出加载和编译成本，冷加载仍约为 O(N)。主体菜单与全策略适配器使用同一份当前记录，只是计算路径不同。

Redis 模式的服务 API 写入成本在保存路径：控制面先取 PostgreSQL advisory lock，在同一 repeatable-read 快照中合并全部 `用户 × 域 × 服务` 来源；Redis 层验证完整输出后，按专用前缀严格 `SCAN`、删除本轮不存在的用户记录，再逐用户 `SET` 完整 JSON。每条用户写入原子，环境或应用批次不整体原子；部分失败可能保留旧权限直到下一轮全量对账。鉴权请求侧没有数据库读取。显式禁用时保存不发布 Redis，鉴权请求读取数据库 current-policy。菜单路径的每次鉴权仍有数据库读取，完整 HTTP 接口延迟不能等同于下面的纯 CPU 匹配耗时；远程服务目录配置还会增加一次目录网络读取。

Redis 模式下服务 API 入口的单条流程：

```text
GET key
    key = PREFIX:<QueryEscape(trim(service))>:<QueryEscape(trim(subject))>[:<QueryEscape(normalized domain)>]
  → String 缺失 / 类型或 JSON 错误 / 身份不匹配 / Redis 错误 → 拒绝
  → 校验大小 / JSON / subject / service_resource / domain
  → 按内容复用本地编译索引
  → 编译完整 Catalog 与合并后的用户 API 并集 → 匹配
```

### 按真实绑定量测试

`BenchmarkRBACBindingVolume` 分别生成以下数据；编译和 fixture 创建不计入暖查询。每组另外增加一个没有任何角色授权的 API，用于验证“用户已绑定但接口未授权”的拒绝路径。

| 场景 | 用户数 | 角色数 | 用户角色绑定 B | 角色接口绑定 G | 业务 API 数 E |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单角色 | 100,000 | 1 | 100,000 | 10,000 | 10,000 |
| 单角色大规模 | 1,000,000 | 1 | 1,000,000 | 100,000 | 100,000 |
| 多角色共享 | 100,000 | 100 | 400,000 | 100,000 | 10,000 |

2026-10-15，Apple M1 Pro / darwin arm64 / Go 1.26.5，单次样本；编译 `-benchtime=1x`，匹配 `-benchtime=250ms`：

| 场景 | 构建一次 | 索引新增保留内存 | 静态允许 | 参数允许 | 轮换用户和接口允许 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单角色，10 万绑定 / 1 万授权 | 19.4 ms | 7.83 MiB | 143.6 ns | 196.6 ns | 263.1 ns |
| 单角色，100 万绑定 / 10 万授权 | 363.7 ms | 112.97 MiB | 141.5 ns | 215.9 ns | 472.4 ns |
| 多角色，40 万绑定 / 10 万授权 | 93.5 ms | 24.74 MiB | 157.6 ns | 204.9 ns | 332.4 ns |

静态和参数基准重复查询同一身份和路径；轮换基准预先生成 4,096 组通过不同步长分散到用户表和接口表的身份及静态/参数路径，循环访问，不把生成字符串算进查询时间。大规模单角色组的已绑定用户无权限拒绝为 147.6 ns，未知用户拒绝为 101.1 ns。

“索引新增保留内存”是在原始 fixture 仍存活时，构建前后执行 GC 后比较 `HeapAlloc`，由 `index_retained_B` 输出；不包含 fixture 本身，以及与 fixture 共享的 subject/路径/编码字符串，不能当作服务进程的总 RSS。三组构建的累计分配分别约 20.9 / 286.0 / 59.6 MB，由 `B/op` 输出，和常驻内存含义不同。允许决策为了返回 `matched_roles` 分配一次切片，单角色 16 B、多角色 64 B；未知用户拒绝无分配。

构建成本和匹配成本必须分开陈述：表中“构建一次”和“索引新增保留内存”属于加载与编译成本，其余列才是匹配成本。冷启动、缓存淘汰或保存后的首次请求都要支付这份加载与编译成本，该层仍随数据量增长，与这次请求实际匹配的接口数量无关。2026-10-15 用同一 fixture 独立复跑单角色 100 万用户绑定 / 10 万接口授权：单次构建约 326 ms、索引新增保留内存约 113 MiB（GC 后 `index_retained_B` 118,655,136），分散身份与接口的纯匹配约 0.82 微秒/次。两组数字都不含数据库、服务目录读取和 HTTP 耗时。

这些是纯 CPU 匹配结果，不包括数据库、Redis、JSON 解码或 HTTP 网络。不能用它们声称完整鉴权接口只有几百纳秒，也不能把基准循环次数当作绑定量。不同机器、GC、身份分布和路径交叉程度都会改变结果。

复现大绑定量基准：

```sh
cd src
go test ./internal/biz -run '^$' -bench 'BenchmarkRBACBindingVolume/.*/compile$' -benchtime=1x -benchmem -count=1
go test ./internal/biz -run '^$' -bench 'BenchmarkRBACBindingVolume/.*/(static_allow|parameter_allow|bound_deny|unknown_deny|distributed_allow)$' -benchtime=250ms -benchmem -count=1
```

旧的 100 / 1,000 / 10,000 条数据基准仍保留用于线性扫描对比，每角色一个用户和一个接口，不能代表上述高扇出场景。原先提到的 **22,500 次是随机正确性对比数量，不是绑定数据量**。

### 正确性与安全边界

`TestRBACLargeFanoutSharesRoleWithoutExpandingUserAPIs` 构建 100,000 用户绑定与 10,000 接口授权，断言全部用户共享单角色对象、接口位图词数只随授权数增长，并将允许及拒绝结果与旧算法比较。另验证用户追加角色不会修改共享集合。

随机对比测试保留 150 份随机权限数据 × 150 个请求，逐字段比较新旧决策；还覆盖参数分支回退、最高具体度冲突、停用具体路由不得降级放行、跨字位图、响应不可修改索引、并发构建、保存后重建、失败重试及按应用 LRU 淘汰。
